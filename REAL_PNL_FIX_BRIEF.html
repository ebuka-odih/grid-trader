1 · The problem, in one paragraph

The bot places real orders on Bybit, but it computes PnL itself as the gross grid spread with zero trading fees, then accumulates that fee-free number into an in-memory wallet. So its internal books drift far above reality. Bybit’s execution WebSocket already delivers the authoritative realized PnL (closedPnl) and fee (execFee) per fill — the code receives them and throws them away. On top of that, the per-fill DB writer reads dict fills with getattr(), so every live trade row is logged as unknown / 0 / 0 / 0 / sim_0. Net effect: the dashboard/DB showed +$359 “profit” over one period while the real account went $100 → $93 (−7%).

2 · How a live fill actually flows (current code)

  1. Place order — multi_grid_manager.py:2682-2693: create_limit_order(...) → level.order_id = order["id"] (Bybit orderId).
  2. Execution WS — multi_grid_manager.py:1358 starts a private WS; _handle_execution() (:1531-1571) parses exec_data which contains closedPnl and execFee, then calls engine.notify_fill(order_id, side, qty, price) — drops closedPnl + execFee
  3. Queue — live_engine.py:755 notify_fill() pushes a dict {order_id, side, qty, price} into _fill_queue.
  4. Process — live_engine.py:457 _process_fill_queue() matches the level by order_id (:521), calls grid_core.process_fill(), appends a dict fill_record to state.fills.
  5. PnL math — grid_core.py:981-1043 process_fill() sets pnl = (fill.price − entry)·qty — no fee, gross only. Accumulates into position.realized_pnl.
  6. Journal per-fill — multi_grid_manager.py:2835-2842 records each new fill with getattr(fill,'side','unknown') etc. on a dict → all defaults.
  7. Cycle close — multi_grid_manager.py:1619-1647 reads engine get_status() (total_pnl = realized + unrealized, still fee-free) and wallet_tracker adds it to balance (wallet_tracker.py:233 add_realized_pnl, :97 restore_realized_pnl).
  8. Position sync — live_engine.py:526 every ~10 s overwrites qty/side/entry_price from the exchange but not realized_pnl → two sources of truth.

1.3 High Reconcile the wallet to real equity (stop accumulating)

wallet_tracker.py already has set_live_balance(equity) (:56-85) — it’s just not called on the hot path; the per-cycle path uses add_realized_pnl() (:233) which is what lets the book drift. Make real equity the source of truth.

  • In the portfolio-status loop and at every cycle close (multi_grid_manager.py around the status print ~1700-1760 and the close path ~1619), call fetch_balance({"type":"swap"}), read info.result.list[].totalEquity, and call wallet_tracker.set_live_balance(equity).
  • Keep add_realized_pnl() only as a fallback when the balance fetch fails (network), and log a WARN when falling back.
  • Throttle the fetch (e.g. once per status tick / ≥10 s) to respect rate limits.
# helper to add near startup balance fetch (manager ~1275)
async def _live_equity(self) -> float | None:
    try:
        bal = await self.grid_calc.exchange.fetch_balance({"type":"swap"})
        for a in bal.get("info",{}).get("result",{}).get("list",[]):
            if a.get("totalEquity"): return float(a["totalEquity"])
    except Exception as e:
        logger.warning(f"live equity fetch failed: {e}")
    return None

Live log emits nonsense: 🤖 Agent: shift_down | Price at -10701% of range, shifting down 1075.1%. Today: 50/72 cycles filled zero orders. Causes to investigate & fix:

  • Grid too wide vs. realized volatility → price never reaches levels. Width should be derived from short-horizon ATR, not a fixed MAX_GRID_WIDTH_PCT=20 ceiling.
  • MIN_MEAN_REVERSION=0.40 / MIN_ENTRY_QUALITY=0.10 gates may admit trending coins where a symmetric grid bleeds.

2.4 High Enforce a fee-aware spacing floor

After Phase 1, fees are visible — now make them a gate. A grid is only +EV if per-level spacing pays for the round-trip: require level_spacing_pct ≥ k × (2 × maker_fee) with k≈3 (Bybit maker 0.02% → require ≳0.12%). Reject/await any candidate grid whose spacing is below the floor in grid_engine.py calculate_grid_levels or the deploy gate in multi_grid_manager.py. This is the real “make each fill profitable” lever — not the center-vs-edge sizing debate in MARTINGALE_IMPLEMENTATION_PLAN.md.

2.5 Critical Per-trade order size, exposure caps & leverage

Owner flagged this directly: each trade reserves ~20%+ of the wallet in margin. Confirmed — and worse: live total exposure is currently 61.2%, over the configured 40% ceiling, so the caps are not being enforced at runtime. This is both a risk problem (one trend wipes a big slice of the account) and a profitability problem (the large notional makes fees material against a thin per-cycle target — directly compounds Phase 1).

PHASE 3 Strategy — Anti-martingale (center-weighted) sizing

Recommendation (data-driven): implement anti-martingale / center-weighted sizing — larger orders near the center, smaller at the edges. Do not implement true martingale (averaging down into adverse moves). Execution order: this phase runs after Phase 1 (you cannot measure it until PnL is fee-accurate) and the Phase 2 sizing/leverage fixes (it must run inside the exposure budget). It is an incremental edge, not a silver bullet — the foundation fixes are what stop the bleeding; this improves the win/loss shape.

3.1 Why center-weighted, and why NOT true martingale

The trade DB makes the call unambiguous. The largest realized-loss bucket in every period is price trending through the grid while the position accumulates against you:

The current code’s progressive_sizing actually grows toward the edge (grid_engine.py:235-240) — i.e. it is wired as true martingale, just disabled (PROGRESSIVE_SIZING_ENABLED=false). This phase inverts it to center-weighted and enables it.

3.2 Core change Invert the sizing factor

grid_engine.py, inside calculate_grid_levels(), the elif progressive_sizing_enabled: branch (~line 232-245):

                dist = min(dist, 1.0)
-               # factor climbs from min_factor (near) to max_factor (far)  ← TRUE MARTINGALE
-               factor = progressive_min_factor + (progressive_max_factor - progressive_min_factor) * (dist ** progressive_curve_power)
+               # factor DECAYS from max_factor (center) to min_factor (edge)  ← ANTI-MARTINGALE
+               factor = progressive_max_factor - (progressive_max_factor - progressive_min_factor) * (dist ** progressive_curve_power)
                factor = max(progressive_min_factor, min(progressive_max_factor, factor))

With min=0.6, max=2.0: center level gets 2.0×, edge gets 0.6× the base qty.

3.3 Critical guardrail Keep it budget-neutral (don’t blow the exposure cap)

The factors multiply qty_per_level. The Phase 2 exposure cap sizes the base assuming flat levels (margin = order_size × num_grids), so a distribution whose factors average > 1.0 will silently exceed the per-trade cap. Two acceptable fixes (pick one):

  • Normalize factors to mean 1.0 — after computing all level factors, divide each by their mean so Σ factor = num_grids. Total reserved margin is then identical to the flat grid; only the distribution changes. (Preferred — keeps the Phase 2 cap math valid untouched.)
  • Or compute total margin from the actual factor sum and feed that into the exposure cap / deploy gate, rejecting the grid if Σ(factor)·order_size > cap.

Add an assertion + deploy log: effective_total_margin ≤ per_trade_cap. This is the one place a sizing strategy can quietly re-introduce the 61%-exposure problem.

3.5 Behavioral guardrails (reuse what exists)

  • Per-side fill cap: adaptive_grid.py max_same_side_fills (default 4) — keep it low so the grid can’t keep loading one side in a trend. This is the anti-martingale safety that stops center-weighting from quietly becoming averaging-down when a trend pins price to one edge.
  • Spike/trend pause: keep the existing spike_detector (spike_threshold_pct, spike_cooldown_sec) active so fills pause during fast moves.
  • Trend filter at deploy: don’t deploy a symmetric grid into a strong trend (ties to Phase 2.3) — sizing can’t save a grid that shouldn’t exist.

  3. Acceptance: center-weighted must show lower drawdown-bucket losses and equal-or-better net PnL after fees. If not, the rollback is one flag: PROGRESSIVE_SIZING_ENABLED=false.
